## 🚨 核心原则（绝对禁止违反）

### 🔴 1. 不做破坏性修改
- 先分析项目现有的数据结构和运转逻辑
- 确保修改不会影响已有的正确逻辑和样式
- **No Spec, No Code**：复杂任务无结构化方案，不开始写代码

### 🔴 2. 绝不修改未提及的地方
- 只修改用户明确指出的部分
- 禁止"顺手"重构、重命名、重排旁边的代码
- 改之前想清楚影响面，宁可多问一句

### 🔴 3. 代码必须真实可运行
- 不写占位伪代码（TODO / pass / 省略实现）
- 要么完整实现，要么明确告知缺少什么才能完成
- 服务于项目真实上线，不做表面完成

### 🔴 4. 专注可信结果，拒绝冗余
- ❌ 不生成无用文档和冗长分析说明
- ✅ 所有算力专注于交付真实可信的代码
- ✅ 回复简洁，直接给结论

### 🔴 5. 上下文管理（重要）
- 上下文使用率 **维持在 50% 以下**
- 一个会话只处理 **一个任务**，用 Git 隔离版本
- 会话出问题时，果断开新会话，不要在烂摊子上继续修

## 💡 提升效率的最佳实践

### 上下文保鲜策略
- 复杂任务先用 `plan` 模式讨论清楚再执行
- 遇到上下文过长的警告 → 立即总结要点，开启新会话继续
- 每次会话聚焦一件事，完成后 commit，再开新会话

### Git 工作流（每次必须）
- 不在主分支直接改代码
- 每个小任务完成就 commit（原子提交）
- commit 前必须编译通过
- 提交格式：`feat/fix/refactor(scope): 中文简述`

### Spec 先行（中等以上任务）
```
1. 明确需求边界（澄清所有疑问）
2. 生成任务拆解清单（Tasks）
3. 用户确认后逐步执行
4. 每步展示可验证的结果（编译/运行输出）
5. 全部完成后沉淀知识到对应规范文件
```

### 知识沉淀（踩坑必记）
- 遇到非常规问题 → 记录到对应子规范文件
- 发现项目特有约定 → 更新下方"项目约定"区域
- 飞轮：`踩坑 → 记录 → AI更准 → 更少踩坑`

## 📌 项目约定

- **项目名称**：CREDINEX-ACCOUNT（信用账户系统）
- **技术栈**：Java 11 / Spring Boot / Gradle / MySQL
- **主分支**：master（禁止直接提交，必须走 feature 分支 + PR）
- **代码风格**：阿里巴巴 Java 开发手册 + `coding-style.md` + `java.md`
- **禁止引入的依赖**：未经确认的新依赖需先询问，不得擅自 `build.gradle` 添加
- **特殊注意事项**：
  - 💰 涉及资金计算的代码**必须使用 `BigDecimal`**，禁止 `double/float`
  - 🗄️ 数据库写操作**必须有 `@Transactional` 事务边界**
  - 🔒 敏感操作（删除 / 金额调整）**需要双人 Review 后才能合并**
  - 📝 日志中涉及用户隐私字段（身份证/手机号）**必须脱敏**
