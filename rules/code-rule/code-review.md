# 代码审查规范 — code-review.md
> 当你需要做 Code Review、审查他人代码、或被要求检查代码质量时，加载本文件。

---

## 🔍 审查维度

按优先级从高到低：

### 🔴 P0 — 必须修复（阻断合并）
- [ ] **逻辑正确性** — 功能是否符合需求，边界条件是否处理
- [ ] **安全问题** — SQL 注入、XSS、越权访问、敏感信息暴露
- [ ] **数据一致性** — 事务边界是否正确，并发场景是否考虑
- [ ] **空指针/异常** — 未处理的 null、未捕获的异常

### 🟡 P1 — 建议修复（可合并但需跟进）
- [ ] **性能问题** — N+1 查询、无索引的大表查询、不必要的全量加载
- [ ] **代码可读性** — 命名是否清晰，逻辑是否易理解
- [ ] **重复代码** — 是否有可以抽取复用的逻辑
- [ ] **错误处理** — 异常是否有合理的处理和日志

### 🟢 P2 — 建议优化（可选）
- [ ] **注释** — 复杂逻辑是否有说明
- [ ] **测试覆盖** — 关键逻辑是否有单测
- [ ] **代码风格** — 是否符合团队规范

---

## 📋 审查清单（快速版）

```
□ 功能逻辑是否正确？
□ 是否有明显的安全漏洞？
□ 事务/并发是否处理正确？
□ 是否有 NPE 风险？
□ 是否有性能隐患（N+1、全表扫）？
□ 命名是否语义清晰？
□ 是否有大量重复代码？
□ 异常处理是否合理？
```

---

## 💬 评审话术规范

**提问式（推荐）**
> "这里为什么选择 X 而不是 Y？"
> "这个场景下如果 XX 为空会怎样？"

**建议式**
> "建议提取成公共方法，后续复用更方便"
> "P1: 这里可能存在 N+1 查询，可以考虑批量查询"

**必须修复**
> "P0: 这里缺少权限校验，任意用户可访问他人数据，需要修复后才能合并"

---

## 🚫 审查禁忌

- ❌ 人身攻击，评论针对人不针对代码
- ❌ 只说"有问题"不说哪里有问题
- ❌ 把个人风格偏好当 P0 问题强制要求
- ❌ 审查范围外的代码大改（除非发现严重 bug）

## 📊 审查总结模板

```
## ✅ 审查总结

- 本次审查文件数：X
- 严重问题：X 个
- 警告：X 个
- 建议：X 个
- 整体评价：一句话总结

## 约束

**必须改**（合并前解决）：
1. [P0] xxx 文件 xxx 行：问题描述

**建议改**（可跟进）：
1. [P1] xxx 文件：建议描述
```
